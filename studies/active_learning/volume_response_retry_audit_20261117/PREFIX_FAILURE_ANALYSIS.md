# 前缀批次的首次失败、方案保真与H1–H5

## 1. 可观察到的触发条件

本轮按真实validator与原始消息复核了540个Free32已接受batch：539有唯一匹配的原始LLM最终答，另1批为已授权人工单ID修正。127个最终前缀案例全部属于前者，且全部最初可解析的方案不是前缀。完整记录率127/540=23.52%；严格原始最终答子集率127/539=23.56%。不能继续把540称为未经人工修改的纯LLM最终方案。

最具体的观察是：**合法候选身份或packet绑定的首错之后，客户端允许完整方案重写，最后落到按salted ID hash展示的前32行。** 不是客户端没有传原方案：1120请求上下文均有精确hash绑定，580次续接保留完整旧消息、完整原答与错误。也不是纠错指令强迫选前32：127例中都没有这样的指令；只有3例最终文本自己明确提到first32，不能把所有模型动机都恢复出来。

首错是validator短路顺序下第一个触发的问题，而不是方案全部错误。原始ID、合法数、首错原文、各turn校验结果、最终保留率与输入/输出长度分别见`retry_case_batches.csv`、`retry_proposals.csv`。

## 2. 540与127两种分母下的首错

| 首次记录错误 | 全540批中的批数 | 最终前缀 | 该首错组前缀率 |

|packet根绑定|9|4|44.44%|

|无保存的首错|277|0|0%|

三个策略分别有68/85/110批记录首错，合计263；其中127变为前缀，另136没有变为前缀。136含一批人工修正，严格原始最终答对照为135。不能拿277个首答成功方案混入“同样出错后”的对照来抬高保留率。

候选身份首错225例中，161例混入当轮已观测ID，97例有不属于H/U的未知ID，0例首轮出现重复ID；分类可以重叠。前缀的123个候选身份首错中分别为110/38/0例。它说明这批数据的身份错误经常是**候选表与已观测证据表的ID角色混淆**，不能将所有错误统称为随机抄写错误，也不能由此判断模型动机。

127例首提议平均有28.61个唯一合法ID，中位数30；38例恰有32个choices、其中31个唯一合法。合法性错误并不意味着需要丢掉全部科学选择。全部原始可解析选点顺序已保存；不可解析文本不使用正则补造候选。本队列1120份保存answer均可解析JSON，但是否符合完整方案规则另行校验。

## 3. 整批重选损失了多少原合法选择？

| 组别 | batch | 原方案唯一合法ID事件 | 最终仍保留 | 加权保留率 |
|---|---:|---:|---:|---:|
|失败后成为前缀|127|3634|440|12.11%|
|失败后非前缀，含人工修正|136|4047|2594|64.10%|
|失败后非前缀，严格原始LLM最终答|135|4016|2563|63.82%|
|首答无记录失败|277|8864|8864|100%|

前缀案例逐批保留率中位数仅6.90%。这个差异证明最终集合的方案保真程度不同，不证明前缀导致多少Row损失：错误难度、科学区域、模型、日期与路径没有随机化。

与C4的交叉核验：离线局部纠错原型能保留3634个原合法唯一ID，占4064个原32名额的89.42%，留下430个必须补充的空额；它不是把前缀替代为另一批自动候选。首错短路还遮住了27例科学证据问题：123个首ID错中25例、4个首binding错中2例仍有未观测证据引用。四个根绑定虽然都可用真实request严格证明并作审计式字段修复，修后仍没有一个原方案完整通过验收，不能把“ID可保留”说成“科学方案全部合法”。

## 4. H1–H5的证据与反例

### H1：完整重生成接口没有约束保留原科学选择

**得到流程支持，因果收益未识别。** 纠错要求返回完整最终JSON，而不是只修某个局部字段；代码没有锁定原有合法choices。完整原答和错误明明都还在上下文里，127例仍从非前缀改成前缀，原合法项只保留12.11%。更准确的机制候选是“方案保真没有被工程协议保障”，不是“模型忘了前文”。少数历史额外授权还明确要求只替换非法ID，不能声称所有指令都鼓励全盘改写。

下一步应测试受约束的局部修复/待补清单能否保持方案与Row价值，而非先修改科学目标。当前原型只证明可以保留已合法内容；430空额及科学证据问题仍需新的判断，本轮没有调用LLM或把原型写回selector。

### H2：前缀与候选展示顺序有关

**集合特征直接成立，顺序因果效应仍未知。** 127例都严格等于真实packet前32行，连顺序一致，且初始可解析提议都不是该前缀。候选表本来按每轮salted ID hash展示，不是科学排序；这是非常具体的顺序依附表现。

但历史没有同一冻结状态下只改变展示顺序的随机化对照。不能由“匹配前缀”推断换顺序一定改善学习，也不能将哈希前缀等同于一次独立随机科学实验。未来可把行顺序作为与CW可见性、服务商分别独立的因子。

### H3：很长全集与纠错负担导致质量下降

**客户端记录的负担很大可证，长度导致前缀不成立为已验证结论。** 首请求返回usage记录的input_tokens为427699–467320（约42.8万–46.7万），全部逻辑节点所记录的最高input_tokens为597535；未独立验证服务端tokenization或计费。客户端messages字符数约83万–144万。New157 r15经历82个保存回答，164条messages，增加约54.9万字符，最后却不是前缀；NoCW6101 r26有22个回答，最后是前缀。两种反例都必须保留。

在各方法的首错批内，按最初输入长度分四组，前缀率不单调：Historical约47.1%/47.1%/17.6%/35.3%；New约59.1%/28.6%/61.9%/38.1%；NoCW约64.3%/44.4%/63.0%/53.6%。不能说“越长越容易前缀”。多次纠错组通常较高，但New的6+回答组只有1/4为前缀；轮数本身也由失败难度与持续重试政策共同产生。客户端白名单响应未保存服务端truncation字段，无法进一步检测服务端实际裁剪。

### H4：特定错误更容易触发前缀

**首错关联明显，且必须区分潜在其他错误。** 127例的首错全部为123个候选身份与4个packet绑定；首证据错误27例没有前缀。它支持优先改善ID角色校验和根绑定处理，但不能将首证据错误组当作更聪明的模型组，或认定ID错误对前缀的因果效应。不同运行、批次、错误难度与后续纠错政策未对齐；短路校验还使前缀中27个证据问题不作为首错出现。

四个binding case均有实际request_00，request/messages/config SHA等于原始turn SHA，user packet与input.json完全相同，packet自绑定正确。因此根hash错不能当作客户端发错了候选池；只修这一字段也不会解决全部科学问题。

### H5：模型/effort、日期、端点和政策解释了频率

**观察异质性可报，不能归因供应商或模型降级。** 按首请求，Historical Astra/high为2/16前缀、Sol/xhigh为23/164；New和NoCW同为Sol/xhigh，却为40/180与62/180。它们同时混杂阶段、记忆、日期、系统提示、验证规则与恢复政策，不能从这些比例估计模型或effort效应。

本轮纠正了先前把New全轨迹当有限8×4的说法：178个New batch有实际persistent标记，逻辑与传输上限后被授权扩展；NoCW也存在额外授权/持续重试。实际只有一个端点主机摘要，没有官方API对照。返回模型字符串是客户端记录，既不能独立认证服务端权重，也不能用于指控降级。传输失败可能发生在连接建立之前，不能当成生成质量事件。

## 5. 可以直接采取的下一步

优先把**工程保真问题**作为独立路线：保留合法、唯一的原选择和原理由，确定性修复可严格绑定的根字段，明确保留证据问题与待补名额。先审核dry-run保真，再设计受约束的少量冻结提案对照；不要用前32自动补齐，不要同时改科学目标、模型、采集规则和provider。

当前证据没有证明所有Free效率差来自前缀，也没有证明更忠实的修复必然提高Row。模型体积响应的15次控制训练属于另一条路线，其正负结果不应被混进本次客户端流程诊断。未来性能确认仍需相同冻结状态下的真实配对训练。
